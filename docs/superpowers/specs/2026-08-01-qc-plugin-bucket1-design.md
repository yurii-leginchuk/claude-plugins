# QC-плагин, первая корзина: автоматизируемые проверки

Дата: 2026-08-01
Статус: согласовано, готово к планированию реализации

## Контекст

Агентство ведёт QC сайтов через MarkUp.io: ревьюер вручную ходит по страницам и оставляет
комментарии. Из воркспейса Poirier Agency извлечена 1000 закрытых (Resolved) правок по 10 сайтам
и классифицирована в `research/markup-io-resolved-taxonomy.md` — 11 групп, ~80 правил.

Разбор показал три вещи:

1. Значительная часть правок **механическая и повторяемая**: формат `tel:`, `target=_blank` на
   внутренних ссылках, отсутствующий H1, дыры в иерархии заголовков, `noindex` на боевой странице,
   Lorem ipsum, битые ссылки, горизонтальный скролл на мобильном. Человек тратит на это часы,
   а правило описывается однозначно.
2. Больше половины правок — **сквозные по сайту** («ACROSS SITE», «should be the same with other
   pages»), то есть проверять одну страницу в отрыве от остальных бессмысленно.
3. Правки повторяются десятками, потому что страницы построены на общих шаблонах Elementor:
   один дефект в футере даёт 47 одинаковых комментариев.

Цель этой итерации — снять с человека первую категорию целиком: то, что проверяется без Figma,
без копи-дока и без смысловой оценки. Сравнение с дизайном и копирайтом — отдельные последующие
итерации, и текущий дизайн не должен им мешать.

Стек проверяемых сайтов зафиксирован: **WordPress + Elementor + Gravity Forms + JetPopup**.

## Решения, принятые при обсуждении

| Вопрос | Решение |
|---|---|
| Откуда site-контекст при QC одной страницы | Кэш-снапшот сайта, с командой очистки |
| Глубина при QC сайта | Браузер по **всем** страницам; сокращение до 1–2 представителей только если шаблонность **доказана** |
| Дев или прод | Дев — основная цель; прод — отдельный узкий проход на логические расхождения |
| Формат результата | HTML-отчёт (Artifact) + `findings.json` |
| Использовать pa-cms MCP | Нет, плагин самодостаточен |
| Движок браузера | Playwright в составе плагина |

## Архитектура

Плагин Claude Code с тремя скиллами-обёртками и одним детерминированным движком на Node.

```
claude-plugins/
  plugins/qc/
    .claude-plugin/plugin.json
    skills/qc-site/SKILL.md
    skills/qc-page/SKILL.md
    skills/qc-cache/SKILL.md
    engine/
      package.json                 # единственная зависимость — playwright
      src/cli.js                   # qc crawl | audit | report | cache
      src/crawl/{discover,fetch,store}.js
      src/parse/page.js
      src/rules/static/<rule>.js
      src/rules/browser/<rule>.js
      src/template/fingerprint.js
      src/report/{json,html}.js
      test/fixtures/
      test/rules/<rule>.test.js
    references/taxonomy.md         # переносится из research/markup-io-resolved-taxonomy.md
```

Файл исследования `research/markup-io-resolved-taxonomy.md` при реализации переезжает в
`plugins/qc/references/taxonomy.md` и становится частью плагина: каждое правило движка ссылается
на свой ID в таксономии, чтобы был виден источник требования.

Разделение ответственности жёсткое: **вся логика проверок живёт в коде движка**, скилл только
собирает вход, запускает движок, читает `findings.json` и оформляет отчёт. Claude не разбирает
HTML «глазами» — иначе результат недетерминирован и не тестируется.

### Контракт правила

```js
export default {
  id: 'E4',
  severity: 'major',
  engine: 'static',              // 'static' | 'browser' | 'prod-diff'
  check(page, site) { return findings }
}
```

`page` — разобранная страница, `site` — снапшот всего сайта (нужен для проверок на дубли и
консистентность). Правило не знает о других правилах и о пайплайне. Добавление правила = новый
файл + новый тест, без изменений в остальном коде.

## Команды

### `/qc-site <вход>`

Вход распознаётся по виду ссылки:

- **URL сайта** — страницы находим сами: `robots.txt` → `sitemap_index.xml` → вложенные sitemap'ы;
  если их нет — обход от главной в пределах хоста с ограничением глубины.
- **Google-таблица** — тянем `export?format=xlsx`, ищем вкладку со списком страниц, колонки
  сопоставляем по смыслу (`URL`, `Dev Link`, `Figma Link`, `Copy Doc Link`, `Page Type`), а не по
  точному заголовку: у разных клиентов имена отличаются. Приоритет у `Dev Link`, боевой URL
  сохраняется рядом как пара для прохода по проду. Если сопоставление колонок неоднозначно —
  показываем найденное и спрашиваем подтверждение до запуска.
- **Только Figma** — для первой корзины неприменима. Сообщаем об этом прямо и просим ссылку на сайт.

Флаги: `--fresh` (игнорировать кэш), `--only <ruleIds>`, `--skip <ruleIds>`,
`--no-template-reduction` (браузер по каждой странице, без группировки),
`--env dev|prod` (переопределить определение среды), `--prod <url>` (задать боевую пару вручную),
`--concurrency <n>` (по умолчанию 6).

### `/qc-page <url> [copy-doc] [figma]`

Copy-док и Figma на этой итерации не используются, но принимаются и сохраняются в снапшот для
следующих итераций. Команда требует снапшот сайта: если его нет — предлагает собрать быстрый
статический (без браузерного прохода); если есть — берёт из него кросс-страничный контекст,
без которого не работают проверки на дубли title/description и на входящие битые ссылки.

### `/qc-cache`

`list` — что закэшировано, размер и возраст. `clear <хост>` — удалить снапшот одного сайта.
`clear --all` — удалить всё.

## Снапшот сайта

Живёт вне репозитория: `~/.qc-cache/<хост>/`, переопределяется переменной `QC_CACHE_DIR`.

```
~/.qc-cache/starshep-dev.patest.website/
  meta.json          # время сборки, версия движка, источник списка страниц, пара prod↔dev
  pages.jsonl        # по строке на страницу: результат статического разбора
  browser.jsonl      # по строке на страницу: метрики из Playwright
  templates.json     # доказанные группы шаблонов
  links.tsv          # результат проверки всех исходящих ссылок
  html/<sha>.html.gz # сырой HTML
  runs/<timestamp>/  # findings.json и report.html каждого прогона
```

Сырой HTML хранится намеренно: новое правило можно прогнать по всему сайту без единого сетевого
запроса. Это же даёт материал для фикстур в тестах.

Снапшот старше 7 дней помечается в отчёте как устаревший и предлагается к обновлению.
Автоматически ничего не перекраулится — решение за пользователем.

## Пайплайн

```
0. Разбор входа        → список страниц (+ пара dev↔prod, если известна)
1. Статический обход   → HTTP-выкачка, HTML в кэш, разбор в pages.jsonl
2. Проверка ссылок     → уникальные URL, HEAD с фолбэком на GET, цепочки редиректов
3. Доказательство      → отпечаток шаблона Elementor, группировка страниц
   шаблонов
4. Браузерный проход   → Playwright, брейкпоинты 360 / 768 / 1024 / 1440
5. Проход по проду     → только логические расхождения с девом
6. Сборка отчёта       → findings.json + report.html
```

### Шаг 1 — вежливость обхода

Сайты свои, но дев-серверы слабые (в правках прямо встречается «the dev server is weak»).
Параллелизм по умолчанию 6 запросов, таймаут 20 с, до 2 повторов на сетевую ошибку и на 5xx.
При появлении 429 или 503 параллелизм автоматически снижается до 2. Настраивается флагом
`--concurrency`.

### Определение среды (дев или прод)

От среды зависит трактовка двух правил, поэтому она определяется явно и показывается в шапке
отчёта. Признаки дева, по убыванию надёжности:

1. хост входит в пару `dev↔prod` из таблицы-стратегии и стоит в колонке `Dev Link`;
2. хост совпадает с `*.patest.website` или содержит сегмент `dev`, `stage`, `staging`, `test`;
3. на большинстве страниц стоит `noindex` либо `robots.txt` запрещает индексацию целиком.

Определённая среда меняет поведение так:

- **дев** — `I4` (noindex) не считается ошибкой; зато ошибкой считаются ссылки и `src` на боевой
  домен, то есть незаменённые абсолютные пути;
- **прод** — `I4` даёт Critical; работает `I14` (следы дева).

Если признаки противоречивы, среда помечается как неопределённая, `I4` и `I14` понижаются до
`confidence: "heuristic"` и не влияют на вердикт. Среду можно задать вручную флагом `--env`.

### Шаг 3 — как доказывается шаблонность

Предположение «страницы похожи, значит это шаблон» недопустимо: страница может быть *сделана по
образцу*, но иметь собственную вёрстку, и тогда её баги уникальны. Поэтому отпечаток страницы —
пара значений:

1. набор ID контейнеров Theme Builder (`elementor-location-*`, `elementor-<ID>`) и подключённых
   `uploads/elementor/css/post-<ID>.css`;
2. хеш скелета: последовательность `data-widget_type` и вложенность контейнеров, **без текста и
   без изображений**.

Правило группировки:

- совпали оба значения → группа доказана, в браузер идут 2 представителя, остальные страницы
  помечаются «покрыто шаблоном T»;
- совпал только хеш скелета, ID разные → группа **не** засчитывается, каждая страница проверяется
  браузером отдельно;
- `--no-template-reduction` отключает сокращение полностью.

В отчёте всегда указывается, сколько страниц проверено напрямую, а сколько покрыто шаблоном.

### Шаг 5 — проход по проду

Выполняется только когда известна пара `dev↔prod` — то есть на входе была таблица-стратегия либо
пара задана флагом `--prod <url>`. Если пары нет, шаг пропускается, и это указывается в отчёте
(молча не пропускаем).

Намеренно узкий, вёрстка прода не проверяется. Ищем только логические расхождения:

- страницы, живые на проде и отсутствующие на деве;
- старые URL, отвечающие 200 (каннибализация);
- расхождения H1 и title между парой dev↔prod;
- редиректы, существующие на проде и отсутствующие на деве.

### Статические

| ID | Проверка | Уровень |
|---|---|---|
| E1 | Битые внутренние ссылки, битые якоря, двойной слэш в URL | Critical |
| E3 | Внутренняя ссылка с `target=_blank`; внешняя без него и без `rel=noopener` | Major |
| E4 | Формат `tel:` — только `+1XXXXXXXXXX`, без пробелов, дефисов, точек | Major |
| E5 | Задвоенный `+1` в номере | Major |
| E6 | `mailto:` с `target=_blank`; телефон или email в тексте без ссылки | Major |
| I1 | Нет H1 или их несколько | Critical |
| I2 | Дыры в иерархии заголовков | Major |
| I3 | H1 картинкой, а не текстом | Major |
| I4 | `noindex` — Critical на проде, ожидаемо на деве | зависит от среды |
| I5 | Canonical: отсутствует, не на себя, http вместо https | Critical |
| I6 | Title: пустой, дубль по сайту, «Home» в главной | Major |
| I7 | Meta description: пустой или дубль по сайту | Minor |
| I8 | Пагинация: номер страницы в URL, canonical и robots на страницах 2+ | Major |
| I13 | Favicon отсутствует или отдаёт не 200 | Minor |
| I14 | Следы дева на проде: ссылки и `src` на `*.patest.website` / `*-dev` | Critical |
| H1 | Оставшийся Lorem ipsum | Critical |
| H7 | Нет `alt` у контентных картинок | Major |
| J1 | Шапка не в `<header>`, нет `<main>` | Major |
| G1 | В форме Gravity Forms нет чекбокса Privacy Policy | Major |
| G3 | Обязательные поля без пометки | Minor |
| G5 | Поле телефона не `type=tel` | Minor |
| S1 | JSON-LD не парсится | Major |

Уточнение по группе G: форма опознаётся по разметке Gravity Forms (`.gform_wrapper`, поля
`.gfield`). `G1` — внутри обёртки формы нет поля-чекбокса, в подписи которого есть ссылка на
страницу политики (`/privacy`, текст «privacy policy»). `G3` — поле помечено классом
`.gfield_contains_required`, но в подписи нет `.gfield_required`. `G5` — поле с типом Phone
отдаёт `input` без `type="tel"`.

### Браузерные (на каждом брейкпоинте)

| ID | Проверка | Уровень |
|---|---|---|
| C1 | Горизонтальный скролл документа | Critical |
| C2 | Элемент шире вьюпорта, с указанием виновника | Major |
| F4 | `cursor:pointer` на неинтерактивном; его нет на интерактивном | Minor |
| F1 | У ссылки или кнопки нет визуальной реакции на `:hover` | Major |
| F5 | Есть изменение на hover, но нет `transition` | Minor |
| J3 | Контраст текста ниже 4.5:1 (крупного — ниже 3:1) | Major |
| B6 | Перекрытие или обрезка элементов | Major |
| X1 | Ошибки консоли и упавшие запросы | Major |
| X2 | Картинка не загрузилась (`naturalWidth = 0`) или осталась `data:`-заглушкой | Major |

### Эвристики, требующие калибровки

`F1`, `J3` и `B6` дают ложные срабатывания по своей природе: hover определяется принудительной
подстановкой псевдокласса и сравнением вычисленных стилей; контраст не умеет в фоновые
изображения и градиенты; перекрытия — самая шумная геометрическая эвристика.

Эти три правила помечаются `confidence: "heuristic"`, выводятся отдельным блоком «требует взгляда»
и **не влияют на вердикт**, пока не будут откалиброваны на реальных сайтах.

## Отчёт

Два артефакта на прогон в `runs/<timestamp>/`: `findings.json` и `report.html`.
HTML публикуется как Artifact.

Схема находки:

```json
{
  "rule": "E4",
  "severity": "major",
  "engine": "static",
  "page": "https://starshep-dev.patest.website/contact",
  "breakpoint": null,
  "selector": "footer a.phone",
  "found": "tel:855-607-8758",
  "expected": "tel:+18556078758",
  "template": "T1",
  "confidence": "high"
}
```

**Отчёт группируется по правилу, а не по странице** — потому что находки сквозные, и разработчику
нужно чинить не 47 страниц, а один шаблон:

> **E4 · Формат `tel:` в HTML** — 47 страниц · все внутри шаблона `T1 (Footer)` → чинится один раз
> найдено `tel:855-607-8758`, ожидается `tel:+18556078758`
> ▸ развернуть список страниц

Ниже — индекс по страницам для точечной проверки, скриншоты только для браузерных находок и только
по представителям шаблонов, приложение «проверено и в порядке».

Дифф с предыдущим прогоном (прогоны и так лежат в кэше): **починено / осталось / появилось новое**.

Вердикт: `Fail` при любом Critical, `Needs fixes` при любом Major, иначе `Pass`.
Эвристики в вердикт не входят.

## Тестирование

Тесты на встроенном `node:test`, без дополнительных зависимостей.

Каждое правило получает фикстуры — **реальный HTML со страниц, где соответствующая правка была
зафиксирована человеком в MarkUp**. То есть тест доказывает, что правило ловит именно тот дефект,
который ловил ревьюер, а не выдуманный случай. Для каждого правила обязательны оба направления:
случай-нарушение и случай-норма (защита от ложных срабатываний).

Отдельно тестируется `template/fingerprint.js`: страницы одного шаблона должны попадать в одну
группу, а страницы с одинаковым скелетом, но разными ID — в разные.

## Границы этой итерации

Не входит и делается позже:

- сравнение с Figma (группа A таксономии) и с копи-доком (H2);
- кросс-страничные проверки консистентности отступов и hover-цветов (B1, B2, F2, I12) — им нужен
  накопленный по сайту набор измерений и статистика выбросов, это следующая итерация;
- выгрузка находок в Asana;
- функциональные проверки JetPopup, слайдеров и фильтров (группа K) — требуют сценариев
  взаимодействия, а не одного снимка страницы.
